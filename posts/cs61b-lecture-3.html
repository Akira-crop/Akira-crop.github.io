CS61B Lecture 3 笔记:List/Array/Map 只是铺垫,引用模型才是这一讲的本体

2026年9月8日
CS61BJava引用数据结构学习笔记

课程:UC Berkeley CS61B(Fall 2026),Lecture 3 "Lists, Arrays, Maps, References"。

这一讲表面上学三种容器(List、数组、Map)加一堆 API,但课程编排的重心其实在后半:变量里到底存的是什么? 上一讲留过一个悬念——x.grow() 之后,为什么从 List 里 get(0) 取出来的对象也变了?这一讲就是揭晓答案的时候。

整讲可以压缩成一条规则,课程叫它 Golden Rule of Equals(GRoE):

赋值复制的是变量中保存的值。对引用类型,这个值是"对象引用",不是对象本身。

笔记分两部分:前半快速过三种容器(重点是选型逻辑,不是 API 清单),后半把引用模型彻底拆开——GRoE、别名、参数传递、二维数组,全部从这一条规则推出来。

一、三种容器:先建立选型直觉

核心特点访问方式长度
List<T>有序、动态增长list.get(i)可变
T[]有序、固定长度array[i]创建后固定
Map<K,V>key → valuemap.get(key)可变

一个统一的看法:List 和数组都是 整数索引 → 值 的映射,Map 只是把索引从整数推广到任意类型(String → Integer、Character → ParticleFlavor)。所以选型规则很自然:

text
顺序 + 长度会变 → List
顺序 + 长度固定 → Array
按 key 查值    → Map

"List 动态、数组固定"的差异在实战里直接决定代码结构。比如"从列表筛出正数返回数组":一开始不知道结果有几个,只能先用 List 收集,数量确定后再建定长数组——这个两段式写法就是两种容器特性的直接产物。

二、泛型:又一处"限制换安全"

老式 raw List 的问题是编译器只能把元素当 Object,list.get(0) 取出来不敢直接赋给 String——因为列表里理论上什么都能塞。泛型解决的就是这个:

java
List<String> animals = new ArrayList<>();
animals.add("cat");
String first = animals.get(0);  // 编译器知道元素是 String
animals.add(123);               // 编译错误,在写代码时就被拦住

值得和 Lecture 1 串起来想:这和静态类型是同一种设计哲学——好的抽象通过限制合法状态来降低程序复杂度。 Python 的 ["cat", 3, True] 很自由,但"这个列表永远只装字符串"这种约束,靠脑子记不如交给编译器维护。类型系统不是敌人,是替你记事的工具。

两个具体坑:

  • List<int> 不存在。 泛型参数不能是基本类型,要用包装类 List<Integer>。int ↔ Integer 的转换(boxing/unboxing)Java 会自动做,平时几乎无感,但写类型参数时必须写 Integer。
  • 三个"长度"写法各不同,混用是高频错误:array.length(字段)、list.size()(方法)、string.length()(方法)。

Map 这边记三点:key 唯一(重复 put 同 key 是覆盖不是并存);Map<K, List<V>> 这种嵌套泛型从里向外读;Map.of(...) 创建的是不可修改的 Map——但注意一个精细的边界:Map 不可修改 ≠ 里面的对象不可修改,m.get(1).lifespan = 5; 依然合法,因为映射结构没变,变的是对象的内部状态。这个区分其实就是引用思维的第一次热身。

三、引用模型:变量是盒子,但盒子里装的不一定是货

CS61B 用盒子模型:每个变量是一个盒子。基本类型(int、double、boolean、char 等 8 种)的盒子里直接装值:

text
int x = 5;        x ┌───┐
                    │ 5 │
                    └───┘

其余几乎所有类型——String、自定义类、List、Map,以及数组——都是引用类型,盒子里装的是指向对象的引用:

text
Walrus a = new Walrus(1000, 8.3);

a ┌───────────┐
  │ reference │────→ ┌───────────────┐
  └───────────┘      │ Walrus object │
                     │ weight = 1000 │
                     └───────────────┘

变量和对象是两个东西,这是全部后续推理的地基。(一个严谨性备注:课件常把引用画成内存地址,那是教学模型。Java 不允许像 C 指针那样直接操作地址,JVM 甚至可能移动对象。稳妥的理解是:引用是一个"能定位到某个对象"的值,画成箭头就够了。)

顺带一个和 Python 的对比:Python 里"万物皆引用",赋值天然就是别名,大家稀里糊涂也这么用过来了;Java 则把世界劈成两半——8 种基本类型一套规则,引用类型另一套规则。正因为两套并存,Java 要求你时刻清楚手里的变量属于哪一边,这也是引用问题在 Java 里显得比在 Python 里更"坑"的原因:不是 Java 更怪,是它把差异显性化了。

四、GRoE:一条规则,两种后果

b = a 永远只做一件事:把 a 盒子里当前保存的值,复制到 b 的盒子里。

基本类型,复制的是数值,之后各走各路:

java
int x = 5;
int y = x;
x = 2;   // y 还是 5,互不影响

引用类型,复制的是引用——于是两个变量指向同一个对象,这叫别名(aliasing):

java
Walrus a = new Walrus(1000, 8.3);
Walrus b = a;      // 复制引用,不复制对象!此刻:两个变量,一个对象
b.weight = 5;      // 通过 b 改对象
// a.weight 也是 5——不是"a 被同步了",是 a、b 一直看着同一只海象

Lecture 2 的悬念在这里正式解开:x.grow() 之后 dogs.get(0) 取出的对象也变了,因为变量和 List 里存的都是引用,从头到尾就只有一只狗。

五、比 GRoE 更进一步:分清"修改变量"和"修改对象"

别名能解释"为什么改 b 影响 a",但解释不了下面这个:

java
Dog a = new Dog(10);
Dog b = a;
b = new Dog(20);   // a 纹丝不动,仍指向 weight=10 的那只

同样是 b,为什么 b.weight = 30 影响 a,b = new Dog(20) 却不影响?因为这两句修改的根本不是同一层东西:

  • b = new Dog(20) —— 修改的是变量 b(盒子里换了一个引用),跟 a 的盒子无关;
  • b.weight = 30 —— 修改的是 b 指向的对象(顺着箭头过去改对象内部),而 a 的箭头也指着它。

遇到任何引用题,先问两个问题就能秒杀绝大多数:①变量是基本类型还是引用类型?②这句代码改的是变量本身,还是变量指向的对象?

六、参数传递:Java 永远是 pass-by-value

这是本讲最容易以讹传讹的地方,直接给结论:Java 只有 pass-by-value,没有例外。 方法调用时,实参盒子里保存的值被复制给形参的盒子——和赋值的 GRoE 是同一条规则,所以引用模型天然覆盖参数传递。三个经典情形:

① 基本类型参数:改不动调用者。

java
static void decrement(int x) { x = x - 1; }
int n = 10;
decrement(n);   // n 仍是 10:形参 x 是独立盒子,复制了数值 10

② 引用参数 + 改对象:调用者看得见。

java
static void grow(Dog d) { d.weight += 10; }
Dog dog = new Dog(20);
grow(dog);      // dog.weight 变成 30:形参 d 复制了引用,两个变量指向同一只狗

③ 引用参数 + 改变量:调用者看不见(试金石)。

java
static void replace(Dog d) { d = new Dog(999); }
Dog dog = new Dog(20);
replace(dog);   // dog.weight 仍是 20!

③是检验"Java 不是 pass-by-reference"的标准题:如果真是按引用传递,d = new Dog(999) 应该能让 dog 换指向。实际不能——因为复制的只是引用值,d 换指向只动了形参自己的盒子。②生效、③失效,恰好共同证明:复制的是值,只不过这个值恰好是引用。

七、null、默认值与两个"没有对象"的区别

引用可以"不指向任何对象",写作 null,对 null 调方法就是著名的 NullPointerException。但有两个状态要分清:

  • 局部变量 Dog d; —— 不是 null,是"未初始化",直接使用会被编译器拦下;
  • 对象的实例字段 —— 会自动默认初始化,引用类型字段默认就是 null。

一个是编译器帮你挡住的错误,一个是合法但运行时才炸的状态,排查 NPE 时这个区分很有用。

八、数组:引用模型的两个推论

推论一:数组也是引用类型,== 比的是引用不是内容。

java
int[] a = {1, 2};
int[] b = {1, 2};
a == b   // false!两个数组两个对象,引用不同

比内容要用 Arrays.equals(a, b)。(这和 Lecture 1 说的"字符串比较用 .equals()"是同一条规则的两个实例——引用类型的 == 永远比身份。)

推论二:二维数组不是矩形表格,是"数组引用的数组"。

int[][] 的准确读法是:元素类型为 int[] 的数组。外层数组的每个格子装的是一个内层数组的引用。这一个模型同时解释三个现象:

java
int[][] x = new int[3][];
x[0] = new int[1];
x[1] = new int[5];     // ragged array:每行长度可以不同,因为每行是独立数组

int[] row = x[1];
row[0] = 99;           // x[1][0] 也变成 99:row 复制的是行引用,又是别名

Particle[][] ps = new Particle[3][4];
// 没有创建 12 个 Particle!只创建了数组和 12 个 null 格子
// 想放粒子,得逐个 new:ps[0][0] = new Particle(...)

第三条是最常见的初学误区:new Particle[10] 创建的是 10 个装引用的空位,不是 10 个对象——容器和内容的区别,又一次回到"变量和对象是两个东西"。

九、综合追踪:四行代码用完全部机制

java
public static void change(Cat c, int x) {
    c.weight += 5;
    x += 5;
    c = new Cat(100);
    c.weight += 1;
}

Cat cat = new Cat(10);
int n = 10;
change(cat, n);
// cat.weight = ?   n = ?

逐步推:

  1. 参数复制:c 与 cat 指向同一只猫(别名),x 独立复制了 10;
  2. c.weight += 5 —— 改对象,共享的猫变成 15(情形②);
  3. x += 5 —— 改形参变量,n 不受影响,仍是 10(情形①);
  4. c = new Cat(100) —— 改形参变量的指向,cat 不动(情形③);
  5. c.weight += 1 —— 新猫变 101,但没有调用者的引用指着它,白改。

输出:15 和 10。能独立推出这道题,引用模型就算过关了。

总结:一张逻辑链

text
三种容器(List 动态 / Array 固定 / Map 按键查值)
   ↓ 它们都是对象,变量存的都是——
引用:变量与对象分离,盒子里装的是箭头
   ↓ GRoE:赋值只复制盒子里的值
别名:两个变量指向同一对象(改对象,人人可见)
   ↓ 区分"修改变量"与"修改对象"
参数传递 = 赋值的特例 → Java 永远 pass-by-value
   ↓ 数组也是引用类型
二维数组 = 引用的数组(ragged、行别名、null 空位全部可推)

一句话压缩:赋值和参数传递都只复制变量中保存的值——基本类型复制数值所以互不影响,引用类型复制箭头所以共享对象;这一讲的每个"奇怪现象",都是这条规则的推论。
